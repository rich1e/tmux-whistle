# tmux-notify 设计方案评审

> 对象：[tmux-notify-design.md](tmux-notify-design.md)（V1 产品设计草案，交互方案 B「终端通知中心型」）
> 对照：tmux-whistle 当前实现（`0592fcf`）
> 日期：2026-10-23

评审只回答三个问题：**哪里不同、哪些值得做、落地到什么程度**。

---

## 0. 结论摘要

这份设计在**产品思考上是成立的** —— 尤其是「已读 ≠ 已处理」和「通知状态与任务状态必须分离」
两条，它指出了 tmux-whistle 真实存在的模型缺陷。但它的**实现栈（SQLite + Python TUI）与本仓
的红线不兼容**，而且在状态栏集成上给出了一个**直接违反已有不变量的方案**。

因此推荐的不是「照做」也不是「不做」，而是：

> **换模型，不换栈。**
> 吸收「两态分离 / 历史 / 精确定位 / 标题正文分离 / run 包装器」，
> 拒绝 SQLite、Python TUI、以及 `#(cmd)` shell-out 状态栏。
> 「通知中心」不作为新的一层 UI，而是把现有的 `list` / `menu` 增强到位。

分档结论：

| 档 | 条目 | 判断 |
|---|---|---|
| **A · 现在就做** | 跳转精确到 pane、标题/正文分离、`run --` 包装器 | 改动小、收益直接、修的是真缺陷 |
| **B · 成组做**（依赖历史） | 已读≠已处理、事件历史、保留策略、通知合并 | 模型正确的部分，必须一起落地才有意义 |
| **C · 做完 B 再定** | 独立的「未读」计数、静音=记录但不提示、Popup 档位 | 都要有历史才成立 |
| **D · 不做** | SQLite、Python TUI 通知中心、`#(cmd)` 状态栏、`capture-pane` 详情、Task/Event 双实体、per-session 静音、`prefix + n` 绑定 | 理由见 §4 |
| **E · 已经满足** | 来源 pane 失效降级、工具无关、显式通知 CLI、状态栏保持轻量 | 文档误以为 V1 要做的事，现有实现已覆盖 |

## 1. 两份设计的定位差异

一句话：

- **tmux-whistle** 是**当前态信号灯**：每个 pane 有一盏灯，状态栏汇总，点一下就灭。
- **tmux-notify** 是**事件收件箱**：事件被记录、分类、检索、归档，看过但不等于处理完。

前者是「**要不要现在看一眼**」的答案，后者是「**上周那次到底怎么回事**」的答案。
两者不是同一个东西的两种实现，而是**覆盖的时间范围不同**：whistle 只有 now，notify 想覆盖 history。

这也是为什么本次评审的分歧点几乎全部集中在 history —— 差异的其余部分要么已经实现，
要么是可以小改补齐的。

## 2. 逐维度对比

### 2.1 状态模型

| | tmux-whistle | tmux-notify |
|---|---|---|
| 建模 | **覆盖式当前态**：`@whistle` = `running`/`done`/`wait`/`error` | **事件溯源** + Task 实体，历史不可覆盖 |
| 粒度 | pane（真源）→ window（聚合）→ global（计数） | 通知记录，每条带 session/window/pane |
| 一个对象能同时是几态 | 一个 pane 只能是一种状态（互斥） | 一条通知可以「失败 且 未读」（正交） |
| 未建模的东西 | 历史、时长、标题、任务身份 | — |

whistle 的互斥性是硬约束：`whistle_aggregate` 取 rank 最高的那个 pane 作为窗口代表，
四个计数来自同一份 `list-panes`。这带来一个很干净的状态栏，也带来一个天花板 ——
**一个 pane 永远只能表达一件事**。「agent 既报了 done 又报了它需要你 review」会被后一条覆盖。

### 2.2 存储与生命周期

| | tmux-whistle | tmux-notify |
|---|---|---|
| 存储 | tmux user option（**server 内存**，不落盘） | SQLite（或 JSONL） |
| tmux 重启后 | **全部丢失** | 仍在 |
| 落盘写入 | 只有调试日志与 detect 守护的 hash/stamp 文件 | 每次事件 |
| 过期清理 | 无（状态会被下一次写入覆盖） | 保留策略 + `cleanup` 命令 |

**这是两者最大、也最真实的差距。** 文档 §11 验收第 8 条（「tmux 重启后持久化通知仍可查询」）
在 whistle 里明确不成立，而且不是 bug —— 是「当前态信号灯」这个定位的必然结果。

顺带一提，文档 §11 验收第 6 条（「来源 pane 被关闭后通知中心仍可用」）在 whistle 里是
**结构性满足**的：pane 的 user option 随 pane 一起消失，不存在悬空条目要处理。

### 2.3 读侧语义 —— 最关键的一处差异

| | tmux-whistle | tmux-notify |
|---|---|---|
| 「已读」 | = 清除状态（`whistle_read_window`） | 独立的 `read` 标志 |
| 「已处理」 | 同上，没有独立概念 | 独立的 `task_status` |
| 读完待处理项 | **待处理数立刻归零** | 待处理数不变，只降未读数 |
| 状态栏三个数 | 🔔N（待处理）+ 四态分布 | ◆N 待处理 / ✖N 异常 / ◉N 未读 |

whistle 把「通知」和「任务」压在同一个字段上，所以焦点进入窗口时只能一次性抹掉。
文档 §5.2 说的正是这件事：

> `Read` 只代表用户看过通知，不代表任务已解决。

**这个批评是对的**，但要补一句上下文：在 whistle 的模型下这个行为是**自洽**的 —— 你切进
那个窗口，就意味着你看见了那个权限提示或那条报错，事情确实处理到一半了。问题在于
一旦你要留历史（§2.2），这个合并就不成立了：**「我瞟了一眼但还没处理」无处安放**。

所以「两态分离」值得做，但**它的前置条件是历史**，单独做没有意义 —— 会变成在 pane option
上再加一个 `@whistle_read` 标记，然后立刻遇到「pane 都没了，这个标记留给谁看」的问题。

### 2.4 定位精度

| | tmux-whistle | tmux-notify |
|---|---|---|
| 菜单跳转 | `switch-client` + `select-window`，**只到窗口** | session → window → **pane** 三级 |
| pane id 是否被记录 | `list` 输出里有（第三列），但 `menu`/`jump` 不用它 | 事件里存 `pane_id` |
| 分屏时能否落到正确 pane | **不能** | 能 |

这是本文档里唯一一个**当下的真缺陷**（其余多是能力缺失）。当前实现里分屏窗口的所有 pane
聚合成一条窗口徽章，`prefix + N` 跳过去后落在该窗口上一个 pane —— 不保证是那个在等的。
`@whistle_border_status` 这个选项正是这个缺陷的权宜之计（把 pane 符号画到每个 pane 顶上），
但它占掉一整行、且默认关。

修起来很小：`whistle_recompute_window` 多写一个 `@whistle_win_pane`，菜单命令加
`select-pane -t %N`。

### 2.5 UI 载体

| | tmux-whistle | tmux-notify |
|---|---|---|
| 主入口 | `display-menu`，26 项硬上限（tmux 单键位上限） | `display-popup` + TUI，无上限 |
| 筛选 | 无 | All / Pending / Failed / Success / Unread 五档 |
| 搜索 | 无 | `/` 本地文本匹配 |
| 详情 | 无 | 独立详情页，含来源、命令、终端输出摘要 |
| 键盘导航 | 数字/字母单键直达 | `j/k` 游标 + Enter 确认 |
| 占用屏幕 | 0（浮在状态栏/窗口标签上） | 85% × 80% 弹窗 |

whistle 的 26 项上限是 tmux 的硬限制（`display-menu` 每项一个单字符键位：9 数字 +
`a`–`q` 17 字母）。这不是实现疏忽，是**载体选型的天花板** —— 对应 TODO-2。

但要看到：`display-menu` 的上限可以靠「`list` 无上限 + 菜单做快捷方式」绕开，而
`display-popup` 的 TUI **不能靠任何办法绕开焦点占用** —— 这是选型层面的差异，不是实现问题。

### 2.6 依赖栈与测试面

| | tmux-whistle | tmux-notify |
|---|---|---|
| 运行时 | POSIX sh + tmux（+ 可选 osascript/notify-send） | Shell + **SQLite** + **Python TUI** |
| 测试 | ShellCheck / shfmt / bats（207 项） | 文档 §11 列了 14 条验收，但未指定 TUI 的测试方案 |
| 风险自陈 | — | §8.1 自己列了「Unicode 宽度、终端尺寸变化、颜色主题」三项待评估风险 |

### 2.7 状态栏集成 —— 这里有一处明确回退

文档 §8.2 建议：

```tmux
set -g status-right '#(tmux-notify status) | %H:%M'
set -g status-interval 2
```

这**违反本仓最贵的一条不变量**：`CLAUDE.md` 原 2 条 ——「徽章必须是纯 tmux format，
一个进程都不 fork」。`#(...)` 每次 `status-interval` tick 都会 fork 一个 shell 进程。

现有实现已经踩过这个坑并给出了正解：整段徽章串预生成进 global option
`@whistle_status_right`，用户配置里只留 `#{E:@whistle_status_right}` 占位符，**运行时零 fork**。
文档 §8.2 建议的方案是把这个正解扔掉、退回到 gpakosz 那种写法。

这一条不是「取舍不同」，是**已知的性能回退**。同理 §8.3 的 `bind n` 建议也要注意：
`n` / `N` 是 tmux 高频常用键。**本仓最终把菜单键定为 `prefix + N`**
（`N` = Notify，实测在你的 `prefix` 表里是空键），见 §4.7。

### 2.8 事件来源

两者在这一项上**没有实质差距**。whistle 的 `tmux-whistle done "消息"` 已经能被任意脚本调用，
Claude Code hook 只是一个更方便的适配器。文档 §12.6「工具无关」这条已经满足。

真正缺的只有一条：**命令包装器**（§6.2 的 `tmux-notify run -- pnpm test`）。
whistle 目前要求用户手写：

```sh
long_job.sh && tmux-whistle done "备份完成" || tmux-whistle error "备份失败"
```

手写这行的出错概率不低（漏了 `||`、`&&` 写反），而且拿不到 duration。

### 2.9 噪音控制

| | tmux-whistle | tmux-notify |
|---|---|---|
| 合并重复事件 | 无 | §4.2 合并成「3 TASKS COMPLETED」 |
| 分级弹窗 | 无（瞬时提示 vs 桌面通知两个固定档） | 成功/失败/等待弹，普通信息默认不弹 |
| 静音 | 只有总开关 `on|off` + 分渠道开关 | Normal / Silent / DND 三档 |

whistle 已经做过一次降噪（TODO-10：`running` 被无条件扇出，用 `whistle_is_notified` 门控掉）。
但**批量场景下的合并还没有** —— 五个 agent 同时完成就是五条横幅依次刷过。

## 3. 值得做的部分

### A 档 · 现在就做

#### A-1 跳转精确到 pane

对应文档 §4.4。这是**当前唯一的真缺陷**，也是 A 档里价值最高的。

- **落点**：`lib/core.sh` 的 `whistle_recompute_window` 增写 `@whistle_win_pane`；
  `bin/tmux-whistle` 的 `cmd_menu` / `cmd_jump` 命令串加 `select-pane -t <pane_id>`。
- **成本**：约 10 行 + 1~2 条集成测试。`whistle_list_lines` 已经输出了 pane id，
  信息不需要新采集，只需在聚合时一并记下来。
- **附带收益**：`@whistle_border_status` 从「分屏时的权宜之计」变回真正的「锦上添花」。

#### A-2 标题 / 正文分离

对应文档 §9 的 `--title` / `--message`。这是**低成本解决一个现存的信息丢失问题**：

现在 `whistle_sanitize` 把消息截到 80 字符（`WHISTLE_MSG_MAX`），长回复被腰斩，
而**没有任何地方能拿到被截掉的部分**。拆成短标题（进徽章与菜单）+ 长正文（进历史/详情）
之后，徽章宽度不再限制能承载的信息量。

- **落点**：`whistle_state_set` 增加一个可选标题参数，多写一个 pane option `@whistle_title`；
  `cmd_set` 增加 `--title`。hook 侧可从 `Stop` 事件里取回复首行做标题、全文做正文。
- **成本**：约 20 行 + 测试。向后兼容：不给 `--title` 时沿用现状（标题 = 截断后的消息）。

#### A-3 `run --` 包装器

对应文档 §6.2。

```sh
tmux-whistle run -- pnpm test
```

自动：进入时置 `running`，退出时按退出码置 `done` / `error`，并把耗时写进消息
（对应文档 Popup 里的 `Duration: 4m 32s`）。

- **落点**：`bin/tmux-whistle` 新增 `cmd_run`，`set -- "$@"` 后直接 exec，
  用 trap 捕获退出码。约 30 行。
- **注意**：这是本仓第一个「必须把退出码和耗时原样传给下游」的路径，
  要确保 `exec` 之后 trap 仍然拿得到状态（用子 shell 而非直接 exec 覆盖）。

#### A-4 顺手修掉与通知中心重叠的两条 TODO

- **TODO-1**（`jump` 不接受裸窗口名）：改 jump 时一并修，awk 加 `$3 == t` 分支，
  但要按 TODO-1 里已写明的约束做 —— 先收集全部匹配、唯一才动手，多命中时报错列候选。
- **TODO-2**（菜单 26 项静默截断）：**加一条提示项**让截断不再静默即可，
  不需要分页 —— 因为 `list` 本身无上限，它已经是全量入口。
  在菜单末尾追加 `- 还有 N 项未显示，用 tmux-whistle list 查看`（`-` 前缀 = display-menu
  的 disabled 语义，绘制时置暗不可选）。

### B 档 · 成组做（前置：历史）

#### B-1 事件历史 —— 不要 SQLite，用一行一条的追加文件

对应文档 §7.2 / §7.3 的**目标形态**，但**不用 SQLite**（理由见 §4.1）。

- **形态**：`$XDG_STATE_HOME/tmux-whistle/events.jsonl`（回落 `~/.local/state/`）。
  每行 `epoch|state|read|session|window|pane|title|body`。
  字段分隔符用 `|`，而 `whistle_sanitize` 已经把 `|` 剔掉了 —— **字段不会互相污染**，
  不需要 JSON 转义，也就不需要在 POSIX sh 里手写 JSON 编码器。
- **并发**：`>>` 追加一行是单次 write，几百字节，远小于 PIPE_BUF，实际原子。
  只有一个写者（agent hook），不存在锁问题 —— 文档 §11 验收第 13 条
  （数据库锁定处理）随之消失。
- **降级**：`@whistle_history on|off`（默认 on）。写失败只 `whistle_log` 一行，
  **绝不影响主路径** —— 历史是增强，不是状态机的依赖。
- **读取**：`awk -F'|'` 过滤 + `cut`。`list --history` / `cleanup` 都在 shell 里完成。
- **容量**：默认保留 200 条（`cleanup` 按文档 §7.4 的策略裁剪：未处理的永不删，
  已处理的留 7 天）。

#### B-2 已读 ≠ 已处理

对应文档 §5.2。**必须在 B-1 之后做**。

- **落点**：pane 上的 `@whistle` 保持「当前态 / 是否待处理」；
  历史行上的 `read` 位由「焦点进入」置 1，**不再连带删除 pane 状态**。
  换句话说：`after-select-window` 钩子从「清除」改成「标记已读 + 重算」。
- **影响的现有行为**：这是**用户可见的行为变更**，需要在 README 里写清楚
  ——「切进窗口后徽章消失，但 🔔 待处理数可能仍在」正是这条变更的体现。
- **需要新增的语义**：什么时候算「已处理」？文档没给。本仓的答案应该是
  **agent 下一次上报状态**（`SessionStart` / `UserPromptSubmit` 会置 `running`，
  自然把上一轮 `done`/`wait` 顶掉）—— 这正好与现有实现一致，不需要新机制。

#### B-3 状态栏引入独立的「未读」维度

对应文档 §4.1 的 `◉ N`。同样依赖 B-1 + B-2。

- **现状**：`🔔N` = 待处理数，与未读是同一个数（因为已读即清除）。
- **改后**：`🔔N`（待处理）与 `◉N`（未读）成为两个独立的数。
- **四态汇总 `●1 ✓1 ◷0 ✗0` 建议保留**：它回答的是「每种状态各有几个」，
  与上面两个「通知属性维度」是正交的，删掉会丢失「哪些 agent 在跑」这个信息。
- 注入点不变（`@whistle_status_right` 一个占位符），自愈逻辑不变。

#### B-4 通知合并

对应文档 §4.2。5 个 agent 同时完成时不该刷 5 条横幅。

- **低成本版本**：`whistle_deliver` 里对瞬时提示与桌面通知做 1~2 秒去抖，
  窗口内累积的状态合并成「N 个任务完成」。**done/wait/error 的合并策略要保守** ——
  文档 §4.2 自己也提醒了 `action_required` 和 `failed` 不该被合并吞掉。
- **依赖**：先有历史（B-1），否则合并掉的那些事件就彻底消失了。

### C 档 · 做完 B 再定

- **静音 = 记录但不提示**（文档 §5.3 的 Silent）：现在 `@whistle_enabled off`
  就是「什么都不干」，因为没有记录可保留。有了历史才有真正的「静音」。
- **Popup 档位**（`display-popup -E`）：`wait` 这种「现在就该来看」的场合，
  比状态栏瞬时提示更醒目。**但它会短暂占屏**，与文档 §12.1「不抢占焦点」有张力 ——
  建议只对 `wait` 开放，且做成可关的选项，默认关。
- **`tmux-notify run` 的 duration 展示**：A-3 已经把耗时记下来了，
  要不要显示、显示在哪，等 UI 形态定了再说。

## 4. 明确不做的部分

### 4.1 SQLite

文档 §7.3 推荐 SQLite，理由是「并发写入、事务、查询与清理」。逐条对照我们的实际形态：

| SQLite 的优势 | 在本场景下的实际价值 |
|---|---|
| 并发写入 | **单写者**（agent hook / 用户脚本），顺序追加 |
| 事务维护 read/dismissed | 追加文件里追加一行「标记已读」即可，不需要事务 |
| 方便筛选与搜索 | 几百条量级，`awk` 足够 |
| 保留历史 | 就是文件本身 |

**代价**是：引入一个二进制依赖（`sqlite3` CLI 或 Python 的 `sqlite3` 模块），
违背 README「运行时零第三方依赖」的定位，且在 macOS 自带 sqlite3 的版本差异上要花时间。

文档 §7.3 自己也给了退路（「原型阶段可以先用 JSONL，但必须处理并发写入、损坏恢复和状态更新」），
而我们连原型都不是 —— 我们要的就是最终形态。

### 4.2 Python TUI 通知中心

三条理由，按重要性排序：

**① 交互哲学冲突。** 文档 §12.1 的第一条是「不抢占焦点」，而 85% × 80% 的
`display-popup` + `j/k` 游标导航**本身就是一次模态接管**。whistle 的定位是
「通知留在视野边缘，你扫一眼、决定要不要过去」；TUI 中心是「把整个屏幕让给通知系统」。
这不是实现质量问题，是两种产品形态。

文档 §11 验收第 10 条「关闭通知中心后原有 tmux 布局不变」在字面上成立，
但它在**打开期间已经改变了**布局。

**② 依赖与测试面。** 项目红线是 POSIX sh + tmux，测试栈是 bats/shellcheck/shfmt。
Python TUI 需要：Unicode 宽度处理、终端 resize、颜色主题、macOS 终端差异 ——
文档 §8.1 自己把这几项列为「选型时重点评估」的风险。这些在 bats 里没法测，
需要引入 pytest + 一个 TUI 测试框架，或者退化成手工验证（等于没有回归保护）。

**③ 增益与代价错配。** TUI 真正提供的新能力是**历史 + 详情 + 搜索**。
这三点里，前两点 B 档做完就有了；第三点（`/` 搜索）在几百条历史上
`grep -F` 就够，不需要模糊搜索。

**替代方案**：把「通知中心」**降级为 `list` 与 `menu` 的增强版** ——
`list` 加 `--pending` / `--all` / `--unread` / `--failed` 筛选与分组，
`menu` 保持单键直达的效率优势。这样 26 项上限、无搜索这些缺点都能绕过，
且不需要新增任何依赖。

### 4.3 `status-right '#(tmux-notify status)'`

见 §2.7。直接违反「徽章零 fork」这条已经踩过坑的不变量，**是回退不是取舍**。

### 4.4 详情视图里的「Recent output」（`capture-pane`）

对应文档 §4.3 详情页的终端输出摘要。这会让**读侧**开始做探测，与本项目
「推送而非轮询」的定位一致：状态来自 agent 的上报，不来自对屏幕内容的猜测。

**廉价替代**：让生产者在上报时自己带上下文。Claude Code 的 hook JSON 里本来就有
`cwd`、`transcript_path`；`--context` 参数让脚本也能带上下文。显示侧只负责消毒与截断。

### 4.5 Task / Event 双实体模型

文档 §7.2 建议 `Task { Events[] }`。在 whistle 的形态里 **pane 就是 task** ——
一个 pane 一个当前状态，历史事件挂在同一个 pane id 上即可。
双实体的价值在于「一个任务跨多个 pane」，那不是这个场景。

采纳的是它背后的那条原则：**「不要把历史事件覆盖成最新状态」**（文档原文），
实现形式是 B-1 的追加日志，而不是两个实体。

### 4.6 按 session / window / pane 分别静音

超出范围。现有 `@whistle_enabled` + 六个分渠道开关已经足够，
再加三层作用域会让「为什么我没收到通知」变成一个难排查的问题。

### 4.7 `prefix + n` / `prefix + N` 绑定

`n` / `N` 是 tmux 里高频占用的键。文档 §8.3 自己也提醒了「应避免覆盖已有绑定」，
但示例用的正是最容易冲突的两个。

> **键位的最终结论。** 评审时这里写的是「现有的 `prefix + W`（W = whistle）应保留」，
> 理由是 `W` 空着、冲突小。键位后来走过两次弯路 ——
> 先改成 `w`，而 `w` 是 tmux 的 `choose-tree -Zw` 默认绑定，**会覆盖掉窗口列表**；
> 再改成 `N`。`N` 在实测的 `prefix` 表里确实是空键，且在空键（`a` `n` `v` /
> `A B G N O Q R S U V W X Y Z`）里助记最直白（Notify）。
>
> 教训：**手动挑键不能靠「看着挺空」**，要跑
> `tmux list-keys -T prefix` 把占用情况全列出来再选。

## 5. 文档本身的问题

评审设计稿时发现的几处内部不一致，实现前需要先定：

1. **§2.1 标题是「V1 功能范围」，表里却混着 V2 优先级的行**（任务监控、Agent 适配器、
   macOS 通知）。§2.3 的 Phase 划分才是真正的范围依据。
2. **UI 里出现了模型里没有的 level**：§4.3 列表项有 `· New message`（普通信息），
   但 §2.1 的 level 只有 success / action / error，§7.1 的事件示例也只有这三类。
   要么补一个 `info` level 并规定它默认不弹窗（§4.2 的表格里是这么写的），
   要么列表视图里去掉这一档。
3. **§11 验收 13（数据库锁定）** 是 SQLite 特有的。采用追加文件后这条自动消失。
4. **§4.2 的 Popup 表格与 §2.1 的优先级表**一致，但 §3 的信息架构说「关闭 Popup 不会删除事件」——
   在没有事件存储的早期阶段（Phase 1）这句话无从谈起，建议按阶段标注。

## 6. 推荐路线

### 6.1 中间方案的形态

不新增任何运行时依赖，不新增任何 UI 层，只在现有分层里加两块：

```
事件生产者（hooks / 任意脚本 / run 包装器）
   │  tmux-whistle <state> [-t pane] [--title T] [--context C]
   ▼
lib/core.sh    ① 写 pane option（真源，当前态）        ← 不变
              ② 追加一行到 events.jsonl（历史）        ← 新增，可关
   ▼
lib/deliver.sh  徽章 / 边框 / 边框状态行 / 瞬时提示 / 桌面通知  ← 不变
   ▼
读侧  menu（精确到 pane）/ jump / list（多筛选维度）      ← 增强
      状态栏：🔔待处理 ◉未读，四态汇总保留                 ← 待处理后改
```

### 6.2 落地顺序

| 阶段 | 内容 | 依赖 | 规模 |
|---|---|---|---|
| 1 | A-1 跳转精确到 pane、A-4 两条 TODO | 无 | 约 15 行 |
| 2 | A-2 标题/正文分离、A-3 `run` 包装器 | 无 | 约 50 行 |
| 3 | B-1 事件历史 + 保留策略 | 无 | 约 80 行 + 新增测试层 |
| 4 | B-2 两态分离 + B-3 独立未读计数 | 3 | 含一次用户可见行为变更 |
| 5 | B-4 通知合并、C 档逐项决定 | 3、4 | — |

阶段 1、2 不改任何现有行为，可以直接做。阶段 3 是分水岭 —— 它让「已读 ≠ 已处理」
变得可表达。阶段 4 需要在 README 里专门写一节说明行为变更。

### 6.3 明确不做的（重述一遍作为边界）

不引入 SQLite、不引入 Python、不引入任何常驻后台进程（`detect` 守护是唯一的例外，
且默认关）、不新增 UI 层、状态栏不做 shell-out、不做 `capture-pane` 探测。

## 8. 一句话验收标准

判断这套吸收是否成功，只看一件事：

> **切进一个窗口之后，🔔 待处理数还在不在，事件还在不在历史里。**

如果做完 B-2，这个问题的答案是「还在，历史里查得到，关掉通知不等于事情被解决了」，
那么本次吸收是成功的 —— tmux-whistle 就同时具备了两份设计各自最好的部分：
whistle 的零依赖与非侵入，notify 的两态分离与历史。

如果为了做到这点而必须引入 SQLite 或 Python TUI，那说明这条路走不通，
应该重新审视「通知中心」这个形态本身。
